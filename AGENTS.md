# Repository Guidelines

## Project Structure & Module Organization
Core source code lives in `src/`. The main library and command-line tools are built from C sources there, with outputs installed to `bin/` by default via `make install`. Regression tests live under `tests/`, with one directory per suite such as `tests/atm_test`, `tests/formod_test`, and `tests/tools_test`; each suite is driven by a `run.sh` script plus control or reference data files. Example workflows are in `projects/examples/limb`, `projects/examples/nadir`, and `projects/examples/zenith`. Documentation sources are under `docs/`, and bundled third-party dependency build scripts live in `libs/`.

## Build, Test, and Development Commands
From the repository root, build bundled libraries first when needed: `cd libs && bash build.sh`. Build the code with `cd src && make -j`; this compiles the executables listed in `src/Makefile`. Run the regression suite sequentially with `cd src && make check`, which executes each `../tests/<name>/run.sh` script. Use `cd src && make clean` to remove binaries and coverage files, and before rebuilding with changed compiler options because Make does not track command-line flag changes. For analysis and docs, use `cd src && make cppcheck`, `make lizard`, `make doxygen`, or `make mkdocs`. Generate coverage with `cd src && make coverage`; that target cleans, rebuilds with `COV=1`, and runs the default tests.

## Coding Style & Naming Conventions
This is a C codebase compiled with strict warnings enabled (`-Werror -Wall -Wconversion ...`) for GCC and Clang. Keep changes warning-free. Match the existing formatting style: two-space indentation, opening braces on the same line for functions and control statements, and concise inline comments such as `/* Allocate... */`. Use `snake_case` for functions and variables, and keep new executable or test names aligned with existing patterns like `obsfmt`, `tblgen`, and `atm_test`. Format C sources and headers from `src/` with `make indent` after a successful build; it rewrites all `*.c` and `*.h` files there, so review the diff and keep only relevant changes. Do not edit generated executables or object files.

Keep code changes small and focused. Before changing behavior, check existing callers, tests, and documented expectations; question assumptions and explain non-obvious choices. Avoid new `static` helper functions: use a macro for a small operation when its arguments can be evaluated safely, or a regular function declared and documented in `src/jurassic.h`. Reuse existing data structures where possible. Before adding a `struct` or changing a data layout, check affected OpenACC host/device transfers, MPI paths, and other consumers of that structure.

## Testing Guidelines
Add or update regression coverage in the nearest existing suite under `tests/`, or create a new `<feature>_test` directory with a `run.sh` entry and reference outputs when needed. Follow the existing Bash test scripts, use `set -euo pipefail`, and write deterministic outputs to local `data/` subdirectories before diffing against checked-in references. Run the narrowest relevant test first, then `cd src && make check` for shared core changes or before opening a PR. `arm_test` and `mpi_test` are separate targets and are not part of `make check`. Investigate failures before changing checked-in references; update only affected baselines after verifying and explaining the new results.

Keep the MkDocs manual in `docs/manual/` and Doxygen API documentation in sync with relevant code, build, and workflow changes. Build affected docs from `src/` with `make mkdocs` and/or `make doxygen` when the tools are available. For new or revised API comments, follow the established `/** ... */` blocks in `src/jurassic.h`: use `@brief` plus a substantive description, document parameters, return values, and behavior where relevant, and always include `@author` with the responsible author's name. Do not invent attribution. Preserve the surrounding style for other comments.

## Commit & Pull Request Guidelines
Recent history uses short, imperative commit subjects such as `Update workflow.` and `Fixed doxygen comments.` Keep subjects concise and specific. Pull requests should describe the scientific or tooling impact, note any changed commands or dependencies, and link related issues. Include sample output or plots when modifying example projects, docs rendering, or user-facing diagnostics. Confirm that GitHub Actions `tests` passes before requesting review.
